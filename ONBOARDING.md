## 1. О курсе

Курс читают эксперты Авито. Большинство студентов уже что-то пробовали с AI на любительском уровне и «вайбкодили» — наша задача не научить «пользоваться нейросеткой», а показать, как AI встраивается в повседневную работу инженера на всех этапах SDLC, и отработать это на практике.

**Сквозной проект.** Через весь курс студент ведёт один проект — **PythonNotify**, Telegram-бот уведомлений о погоде, — развивая его от идеи до продакшена. Каждая неделя добавляет новый слой.

**Каркас курса — EJM.** Engineer Journey Map связывает конкретный AI-инструмент с реальным этапом разработки: требования → дизайн → реализация → тестирование → CI/CD → эксплуатация. Это не одна лекция, а сквозная структура всего курса.

**Что формируем у студента.** Мышление «AI-augmented engineer»: инженер выступает архитектором и тимлидом для своих AI-ассистентов — ставит задачи через промпт-инжиниринг, управляет контекстом (MCP, правила проекта), проводит строгое код-ревью сгенерированного кода и автоматизирует процессы, а не только пишет код.

## 2. Как устроен курс

Ритм: чередование недель «лекция + практика» и недель приёмки лабораторных работ. Приёмки — на неделях 3, 6, 9 и 12. Практики привязаны к сквозному проекту; на приёмках студенты защищают то, что сделали за предыдущий блок.

### Семинар и практика — в чём разница

- **Семинар (разбор).** Разбираем артефакты и требования — User Stories, DoR/DoD, Acceptance Criteria, test plan — и фиксируем улучшения.
- **Практика (hands-on).** Пишем кусок функциональности проекта в коде по циклу «контекст → задача → ревью → уточнение».
- **Сопровождение.** Работаем с правилами проекта (Constitution / AGENTS / MCP), чтобы агент не «галлюцинировал», а изменения были воспроизводимыми.

## 5. Формат практики (для семинаристов)

**Длительность: 90 минут + домашнее задание.** Каркас занятия — тот же цикл, которому учим студентов:

- **Контекст.** Напоминаем, где мы в проекте и какой артефакт/фичу делаем сегодня.
- **Задача.** Ставим агенту задачу структурированно (R.C.T.F. / правила проекта).
- **Ревью.** Критически смотрим на то, что сгенерировал AI: риски, стиль, тесты, edge cases.
- **Уточнение.** Итеративно дорабатываем — «первая версия редко идеальна».

**Типовые точки, где студенты застревают:** `【ЗАПОЛНИТЬ: 2–3 частых затыка по каждой практике — попросить у авторов практик】`.

## 6. Проверка домашних работ (для ревьюеров)

**Ориентир по времени: 15–20 минут на студента.** Каждая практика сопровождается рубрикой, эталонным решением и чек-листом.

### Что проверяем

- Артефакты требований: User Stories, Acceptance Criteria (Gherkin), DoR/DoD, test plan.
- Код фич сквозного проекта (FastAPI-сервис, интеграции, рефакторинг).
- Тесты: unit / API / E2E; осмысленность покрытия, а не только цифру ~90%.
- CI/CD и автоматизации (GitHub Actions, N8N-workflow).
- Понимание, а не «AI-слоп»: студент должен объяснить, что и зачем сделал агент.

### Чек-лист проверки (скелет)

`【ЗАПОЛНИТЬ: проставить критерии и баллы под каждую практику — вынести из README_INSTRUCTORS.md】`

- [ ] Артефакты присутствуют и соответствуют требованиям недели — __ / __ баллов.
- [ ] Код запускается, соответствует спецификации и правилам проекта — __ / __.
- [ ] Тесты проходят и покрывают ключевую логику (в т.ч. edge cases) — __ / __.
- [ ] Процесс задокументирован (как ставились задачи агенту, как шло ревью) — __ / __.
- [ ] Самостоятельность и понимание материала — __ / __.

### Как оформлять обратную связь

- Где выставлять оценки: `【ЗАПОЛНИТЬ: ведомость / таблица / LMS — указать инструмент】`.
- Срок возврата проверки: `【ЗАПОЛНИТЬ: напр. в течение N дней после дедлайна】`.
- Тон и формат фидбэка: `【ЗАПОЛНИТЬ: шаблон комментария — что хорошо, что улучшить, что критично】`.

### Пограничные случаи — что делать

- Опоздания: `【ЗАПОЛНИТЬ: политика по срокам и штрафам】`.
- Плагиат / полностью сгенерированная работа без понимания: `【ЗАПОЛНИТЬ: процедура и к кому эскалировать】`.
- Спорная оценка: `【ЗАПОЛНИТЬ: как разрешаем — куратор / вторая проверка】`.

## 7. Сквозной проект PythonNotify

Telegram-бот уведомлений о погоде, который студент собирает по слоям в течение курса:

- **Недели 1–2.** Планирование, архитектура, детализация требований и критериев приёмки.
- **Недели 4–5.** Реализация API с кодинг-агентом (FastAPI), правила проекта (MCP), интеграция внешнего погодного API.
- **Недели 7–8.** Расширение контекста, рефакторинг (Spec-driven), ассистент код-ревью для PR.
- **Недели 10–11.** Тесты с помощью AI (~90% покрытия), автоматизация поддержки: баг-репорт → Issue + метрики пользы.

**Технический стек:** Python 3.8+, FastAPI, Pydantic; REST + OpenWeatherMap API + Telegram Bot API; pytest/coverage; GitHub Actions; PlantUML/Mermaid для диаграмм.

## 11. FAQ

**Студент принёс код, который явно целиком сгенерирован — это ок?**
Генерация — норма курса; проверяем не «написал ли сам», а понимает ли, умеет ли ревьюить и объяснить решения. Красный флаг — не «AI написал», а «студент не может объяснить, что сделал агент».

**Что делать, если на практике падает инструмент / нет доступа к модели?**
`【ЗАПОЛНИТЬ: резервный план — запасной провайдер, заранее подготовленные артефакты, к кому писать】`

**Насколько строго требовать ~90% покрытия тестами?**
Цель — осознанное покрытие ключевой бизнес-логики и edge cases, а не цифра ради цифры. Ориентир, а не жёсткий порог.

**Куда писать вопрос по содержанию конкретной практики?**
Автору этой практики (см. раздел «Роли»); организационные — кураторам.
