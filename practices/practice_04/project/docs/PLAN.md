# «Сроки» — self-hosted трекер дедлайнов

Однопользовательское приложение для учёбы и работы: курсы/проекты, дедлайны с приоритетом
и статусом, группировка по срочности, экспорт в календарь (iCalendar). Запускается одной
командой `python3 backend/server.py`, без внешних зависимостей.

Этот файл — **единственный источник правды по API-контракту**. Менять контракт может только
оркестратор; агенты предлагают изменения в отчёте после итерации.

## 1. Границы проекта

Входит: категории (курс/проект), дедлайны (CRUD, статус, приоритет), фильтры/поиск,
сводка (просрочено/сегодня/неделя), экспорт `.ics`.

Не входит (сознательно): авторизация и мультипользовательность (сервер по умолчанию
слушает `127.0.0.1`), уведомления, повторяющиеся дедлайны, подзадачи, вложения.

Ориентир по размеру: бэкенд ~600–800 строк кода + тесты, фронтенд ~900–1200 строк суммарно.

## 2. Архитектура

```
браузер ──HTTP──▶ backend/server.py (ThreadingHTTPServer)
                    ├─ /            → статика из frontend/ (FRONTEND_DIR)
                    └─ /api/...     → JSON-обработчики ──▶ backend/db.py ──▶ SQLite (data/app.db)
```

### Файлы
- `backend/db.py` — соединение, миграции, функции-репозитории (без HTTP). Валидация данных
  (`ValidationError`), `NotFoundError`, `ConflictError`.
- `backend/server.py` — роутинг, разбор JSON, коды ответов, логирование, раздача статики,
  `.ics`-экспорт, точка входа (`main()`).
- `frontend/index.html`, `frontend/style.css`, `frontend/app.js` — SPA без сборки.
- `tests/test_db.py`, `tests/test_server.py` — `unittest`; сервер поднимается на порту 0
  с временной БД и временным `FRONTEND_DIR`.

### Конфигурация (переменные окружения)
| Переменная     | По умолчанию          | Назначение              |
|----------------|-----------------------|-------------------------|
| `HOST`         | `127.0.0.1`           | адрес                   |
| `PORT`         | `8000`                | порт                    |
| `DB_PATH`      | `data/app.db`         | файл БД                 |
| `FRONTEND_DIR` | `frontend` (рядом с backend/) | каталог статики |

Пути по умолчанию считаются относительно корня проекта (родитель `backend/`), а не CWD.

### Схема БД (миграции через `PRAGMA user_version`)
Миграция 1:
```sql
CREATE TABLE IF NOT EXISTS categories (
  id         INTEGER PRIMARY KEY,
  name       TEXT NOT NULL UNIQUE COLLATE NOCASE,
  kind       TEXT NOT NULL CHECK (kind IN ('study','work','other')),
  color      TEXT NOT NULL DEFAULT '#888888',
  created_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS deadlines (
  id           INTEGER PRIMARY KEY,
  title        TEXT NOT NULL,
  description  TEXT NOT NULL DEFAULT '',
  due_at       TEXT NOT NULL,              -- 'YYYY-MM-DDTHH:MM', локальное время сервера
  category_id  INTEGER REFERENCES categories(id) ON DELETE SET NULL,
  priority     INTEGER NOT NULL DEFAULT 2 CHECK (priority IN (1,2,3)),
  status       TEXT NOT NULL DEFAULT 'todo' CHECK (status IN ('todo','in_progress','done')),
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,
  completed_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_deadlines_due ON deadlines(due_at);
```
Чужие таблицы в существующей БД (например, `notes`) не трогать.

## 3. API-контракт (v1)

Общее: префикс `/api`, тело и ответ — JSON (`Content-Type: application/json; charset=utf-8`).
Ошибки: `{"error": "человекочитаемое сообщение по-русски"}`, при ошибке валидации поля —
дополнительно `"field": "<имя поля>"`. Коды: 200, 201 (создано), 204 (удалено, без тела),
400 (невалидный JSON/поле), 404, 405, 409 (конфликт, напр. дубль имени категории), 500.
Даты-время: `due_at` — `YYYY-MM-DDTHH:MM`; служебные `created_at`/`updated_at`/`completed_at` —
`YYYY-MM-DDTHH:MM:SS` (локальное время сервера).

### Объекты
```jsonc
// Category
{ "id": 1, "name": "Матанализ", "kind": "study", "color": "#3366ff",
  "created_at": "2026-10-06T21:00:00", "open_count": 3 }   // open_count — не done

// Deadline
{ "id": 7, "title": "Сдать ДЗ 3", "description": "", "due_at": "2026-10-10T23:59",
  "category_id": 1, "priority": 3, "status": "todo",
  "created_at": "...", "updated_at": "...", "completed_at": null,
  "is_overdue": false }           // вычисляется: status != done и due_at < now
```

### Эндпоинты
| Метод  | Путь                       | Описание |
|--------|----------------------------|----------|
| GET    | `/api/health`              | `{"status":"ok","version":"1"}` |
| GET    | `/api/categories`          | список, сортировка по `name` |
| POST   | `/api/categories`          | `{name, kind, color?}` → 201 Category; дубль имени → 409 |
| PATCH  | `/api/categories/{id}`     | частичное обновление → 200 Category |
| DELETE | `/api/categories/{id}`     | 204; дедлайны остаются без категории |
| GET    | `/api/deadlines`           | список (см. фильтры) |
| POST   | `/api/deadlines`           | `{title, due_at, description?, category_id?, priority?, status?}` → 201 |
| GET    | `/api/deadlines/{id}`      | 200 Deadline |
| PATCH  | `/api/deadlines/{id}`      | частичное обновление; переход в `done` ставит `completed_at`, выход из `done` — обнуляет |
| DELETE | `/api/deadlines/{id}`      | 204 |
| GET    | `/api/stats`               | `{"overdue":n,"today":n,"week":n,"open":n,"done":n}` |
| GET    | `/api/export.ics`          | `text/calendar`, все не-done дедлайны как VEVENT (фильтры те же, что у списка) |

Фильтры `GET /api/deadlines` (все необязательны, комбинируются через AND):
- `status` — `todo|in_progress|done|open` (`open` = не done); по умолчанию все;
- `category_id` — число или `none` (без категории);
- `q` — подстрока в `title`/`description`, без учёта регистра;
- `from`, `to` — границы `due_at` включительно (`YYYY-MM-DD` или `YYYY-MM-DDTHH:MM`);
- `sort` — `due` (по умолчанию, по возрастанию), `priority` (убыв., затем due), `created`.

Семантика `stats`: `today` — не-done с `due_at` в текущих сутках (включая уже просроченные
сегодня), `week` — не-done в ближайшие 7 суток от now, `overdue` — не-done с `due_at < now`.

Валидация: `title` 1–200 символов после `strip`; `description` ≤ 5000; `name` 1–60;
`color` — `#rrggbb`; `kind`/`status`/`priority` — из перечислений; `category_id` должен
существовать (иначе 400 с `field: "category_id"`); неизвестные поля → 400.

### Уточнения контракта (v1.1, после итерации 1)
- Списки (`GET /api/deadlines`, `GET /api/categories`) возвращают **голый JSON-массив**, не `{items: [...]}`.
- `category_id: null` допустим в POST (равно отсутствию поля) и в PATCH (= снять категорию).
- `description: null` → 400 (ожидается строка; пустая строка допустима).
- `PATCH` с `{}` → 200 и объект без изменений.
- Уникальность и сортировка категорий по `name` — без учёта регистра, включая кириллицу
  (проверка в Python через `casefold()`).
- 409 на дубль имени категории содержит `field: "name"`; 404/405/500 тоже возвращают тело `{"error": ...}`.
- Тело запроса больше 1 МБ → 413 `{"error": ...}`.
- `due_at` в ответах всегда ровно `YYYY-MM-DDTHH:MM`; на вход принимается только этот формат.

### Уточнения фильтров (v1.2, после итерации 2)
- `sort=created` — по убыванию (новые первыми), при равенстве — по `id` убыв.
- Неизвестные query-параметры игнорируются; пустое значение (`status=`) = параметр отсутствует.
- Дата без времени: в `from` = 00:00, в `to` = 23:59. `from` > `to` → 400, `field: "to"`.
- Несуществующий `category_id` в фильтре → пустой массив (не 400).
- 400 по фильтру: `field` = имя query-параметра.

### Экспорт `.ics` (v1.3, после итерации 3)
- По умолчанию `status=open`; остальные фильтры — как у списка; невалидный фильтр → 400 JSON.
- VEVENT: `UID:deadline-{id}@sroki`, `DTSTAMP` в UTC, `DTSTART` = `due_at`, `DTEND` = +30 мин
  (floating local time), `SUMMARY`, `DESCRIPTION` (если не пусто), `CATEGORIES`,
  `PRIORITY` (3/2/1 → 1/5/9), `STATUS:COMPLETED` для явно запрошенных done.

## 4. Фронтенд (UX) — v2: календарь

Решения пользователя (2026-10-06): вид-список заменяется календарём; виды «Месяц» и «Неделя»;
боковая панель со срочным; быстрое добавление в ячейке и окно дня; визуальный стиль —
новый (от «тетради в клетку» отказываемся целиком).

Экран на всю высоту окна (`100dvh`), без прокрутки страницы на десктопе:
- **Шапка-тулбар:** «‹ Сегодня ›», название периода («Октябрь 2026» / «6–12 окт. 2026»),
  переключатель «Месяц / Неделя», фильтр категории, поиск, «Категории», экспорт `.ics`.
- **Календарь (основная область):**
  - *Месяц* — сетка 7 × 5–6 недель, неделя с понедельника, дни соседних месяцев приглушены,
    «сегодня» выделено. В ячейке — дедлайны дня (время, название, цвет категории, приоритет,
    просроченные/выполненные различимы), при переполнении — «ещё N», открывающее окно дня.
  - *Неделя* — 7 колонок-дней на всю высоту, дедлайны дня списком по времени (без почасовой сетки).
  - Данные периода — один запрос `GET /api/deadlines?from=<первый видимый день>&to=<последний>`
    (+ `category_id`, `q`), без фильтра статуса.
- **Быстрое добавление:** клик по пустому месту ячейки дня (или Enter на сфокусированном дне)
  открывает поле ввода прямо в ячейке; Enter — создать дедлайн на этот день в 23:59,
  Esc — отмена. Ошибки — у поля.
- **Окно дня** (`<dialog>`): по клику на номер дня или «ещё N» — все дедлайны дня, у каждого
  «готово», изменить, удалить; кнопка «Добавить» на этот день.
- **Диалог дедлайна** — полное редактирование (название, дата и время, категория, приоритет,
  статус, заметки), удаление с подтверждением. Открывается по клику на дедлайн в ячейке.
- **Боковая панель** (справа на десктопе, сворачивается; на мобильном — под календарём):
  сводка `/api/stats`, «Просрочено» и «Ближайшие 7 дней» (по `status=open`), клик — переход
  к дню и открытие дедлайна.
- **Категории** — существующий диалог управления категориями (логику сохранить, оформление новое).
- **Мобильная вёрстка (< 48rem):** месяц — компактная сетка с точками-маркерами дедлайнов,
  тап по дню открывает окно дня; неделя — дни вертикальным списком.
- Клавиатура: стрелки перемещают фокус по дням сетки, Enter — быстрое добавление,
  `T` — сегодня, `PageUp/PageDown` — период назад/вперёд.

## 5. План работ

Работа идёт параллельно: бэкенд — в основной копии репозитория (ветка `Practice_04`),
фронтенд — в git worktree (ветка `practice04-frontend`). Файлы не пересекаются
(`backend/`, `tests/` ↔ `frontend/`). После каждой итерации агент отчитывается
оркестратору: что сделано, отклонения от контракта, вопросы к другой стороне.

### Бэкенд
1. **Ядро.** `db.py`: соединение, миграции, CRUD категорий и дедлайнов с валидацией;
   `server.py`: роутинг, JSON, ошибки, логирование, статика из `FRONTEND_DIR`, все CRUD-эндпоинты.
   Тесты `test_db.py` + базовые `test_server.py`.
2. **Запросы.** Фильтры/поиск/сортировка списка, `is_overdue`, `open_count`, `/api/stats`,
   переходы статусов и `completed_at`, полный набор HTTP-тестов (коды ошибок, 404/405/409).
3. **Экспорт и полировка.** `/api/export.ics` (RFC 5545: экранирование, CRLF, свёртка строк),
   README с запуском, чистый `pyright`, все тесты зелёные.

### Фронтенд
1. **Каркас и дизайн.** Визуальное направление (скил `frontend-design`), разметка, токены,
   `api`-слой, список дедлайнов, диалог создания/редактирования/удаления. Проверка против
   временного мок-сервера в scratchpad (не в репозитории) либо реального бэкенда.
2. **Логика.** Группировка по срочности, относительное время, фильтры и поиск, сводка,
   управление категориями, быстрая отметка «готово».
3. **Полировка и интеграция.** Пустые/ошибочные состояния, ошибки полей, клавиатура и a11y,
   тёмная тема, мобильная вёрстка, ссылка экспорта; прогон против реального бэкенда.

### Фронтенд v2 (календарь)
1. **Новый стиль и календарь.** Новое визуальное направление (скил `frontend-design`),
   каркас на всю высоту, тулбар и навигация по периодам, виды «Месяц» и «Неделя» с
   данными из API, диалог дедлайна, боковая панель со сводкой.
2. **Взаимодействие и полировка.** Быстрое добавление в ячейке, окно дня, категории,
   клавиатура, мобильная вёрстка, состояния загрузки/ошибок, прогон на реальном бэкенде.
Ориентир по размеру фронтенда — до ~1600 строк суммарно.

### Фронтенд v3 (Svelte) — решение пользователя 2026-10-07
Фронтенд переписывается на **Svelte 5 + Vite + TypeScript** (npm разрешён, правила — в
`.claude/rules/frontend.md`). Функциональность и UX — как в разделе 4 (календарь v2);
общий визуальный вид v2 сохраняется, но его нужно **сильно улучшить**: типографика, ритм и
отступы, цвет и контраст, состояния (hover/focus/active/disabled/загрузка/пусто/ошибка),
микроанимации с учётом `prefers-reduced-motion`, тёмная тема, мобильная вёрстка.
Визуальная проверка — в реальном браузере через Claude in Chrome (скриншоты, консоль, сеть).

Сборка и раздача:
- `frontend/` — Vite-проект: `package.json`, `vite.config.ts`, `index.html`, `src/main.ts`,
  `src/App.svelte`, `src/app.css`, `src/lib/` (api, даты, состояние), `src/components/`.
- `npm run build` → `frontend/dist/`; бэкенд по умолчанию раздаёт `FRONTEND_DIR=frontend/dist`.
- `npm run dev` — Vite на `127.0.0.1:5173`, прокси `/api` → `SROKI_API` (по умолчанию
  `http://127.0.0.1:8002`).
- Ориентир по размеру — до ~2600 строк в `src/`, включая CSS в `.svelte` (без тестов и lock-файла).
- Тема: системная по умолчанию + ручной переключатель «системная / светлая / тёмная»
  (`<html data-theme>`, выбор в localStorage с try/catch).
- Шрифт: локальный через `@fontsource/*` (OFL), см. `.claude/rules/frontend.md`.

Итерации:
1. **Порт на Svelte.** Каркас Vite-проекта, `api.ts` с типами, перенос логики v2 в
   компоненты и чистые модули с тестами vitest, паритет функций с v2.
2. **Визуальная переработка.** Сильное улучшение вида с проверкой в Chrome на десктопе и
   мобильной ширине, светлая и тёмная темы.
3. **Полировка и интеграция.** Клавиатура и a11y, состояния ошибок и загрузки, прогон
   сценариев в Chrome против реального бэкенда на собранном `dist/`.

Бэкенд под v3 (одна итерация): `FRONTEND_DIR` по умолчанию `frontend/dist`; понятная
HTML-страница 503, если сборки нет («выполните `npm ci && npm run build` в frontend/»);
`Cache-Control: public, max-age=31536000, immutable` для `/assets/*` (хэшированные имена
Vite), `no-cache` для остального; MIME для `.woff2`, `.webp`, `.ico`, `.map`; тесты; README.

### Финал (оркестратор)
Замена `frontend/` в основной копии версией из worktree (старая — в корзину), общий прогон тестов и ручная проверка,
удаление worktree — по согласованию с пользователем. Коммиты делает пользователь.
