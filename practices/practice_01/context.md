## Context Pack для первого рабочего сценария

Ниже — только то, что меняет выполнение задачи для этого PR. Правила репозитория про `snake_case` в таблицах БД и про i18n frontend-строк сюда **не** перенесены: в diff нет ни схемы БД, ни frontend-кода, поэтому они не влияют на разбор.

### Факты и правила

Факты из diff:

- `app/api.py` — добавлен эндпоинт `POST /api/reviews`, тело принимается как нетипизированный `dict`, значение берётся как `payload["diff"]`.
- `app/api.py` — обработчик возвращает результат `review_service.review(...)` напрямую, без `response_model`.
- `app/review_service.py:14` — `ReviewService.review` подставляет `diff` в f-строку промпта и передаёт его во внешний LLM как есть.
- `app/review_service.py` — вызов `self.llm.generate(prompt)` не обёрнут ни в timeout, ни в обработку исключений.
- `app/review_service.py` — возвращается `{"comment": answer}`: один текстовый ключ.
- В diff нет логирования, нет тестов на новый эндпоинт.

Правила репозитория, применимые к этому PR:

- `SEC-1`: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
- `API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413.
- `REL-1`: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
- `OUT-1`: ответ содержит `summary`, массив `risks` и массив `checks`. В `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`.
- `SCOPE-1`: сервис только советует; он не пишет код и не выполняет действия в GitHub.
- `QA-1`: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.
- `OBS-1`: в лог пишутся только `request_id`, длительность и статус. Содержимое diff и ответа модели не логируется.

Сопоставление diff и правил — основа всех находок:

| Правило | Состояние в PR | Доказательство |
|---|---|---|
| `SEC-1` | нарушено | `app/review_service.py:14` — `diff` уходит в промпт без редакции |
| `API-1` | не реализовано | в diff нет проверки длины `diff` и ответа 413 |
| `REL-1` | не реализовано | `llm.generate` без timeout и `try/except` |
| `OUT-1` | нарушено | возвращается `{"comment": str}` вместо `summary` / `risks` / `checks` |
| `SCOPE-1` | соблюдено | сервис только возвращает текст, действий в GitHub нет |
| `QA-1` | не реализовано | нет механизма привязки риска к строке или правилу |
| `OBS-1` | не реализовано | логирования в diff нет; риск появится вместе с ним |

### Формат входа и результата

- Вход: JSON `{ "diff": string }`, длина `diff` ≤ 20 000 символов (`API-1`).
- Результат (`OUT-1`):

```json
{
  "summary": "string",
  "risks": [
    {"file": "app/review_service.py", "line": 14, "evidence": "строка diff", "risk": "нарушение SEC-1"}
  ],
  "checks": ["string"]
}
```

- `risks` — не более трёх элементов, каждый с полями `file`, `line`, `evidence`, `risk`.
- Коды ответов: 200 — успех; 413 — diff больше 20 000 символов (`API-1`); 422 — нет поля `diff`; контролируемый ответ при ошибке LLM (`REL-1`).

### Ограничения и запрещённые действия

- Нельзя отправлять diff во внешний LLM без удаления токенов, паролей и приватных ключей (`SEC-1`).
- Нельзя возвращать больше трёх рисков и нельзя возвращать риск без `file`, `line`, `evidence` (`OUT-1`).
- Нельзя включать риск, не подтверждённый строкой diff или правилом репозитория (`QA-1`).
- Нельзя делать approve, merge, коммитить код или выполнять любые действия в GitHub (`SCOPE-1`).
- Нельзя писать в лог содержимое diff или ответа модели (`OBS-1`).
- Нельзя ждать внешний LLM дольше 10 секунд (`REL-1`).

### Хороший пример

```text
app/review_service.py:14 — diff отправляется во внешний LLM без удаления секретов,
что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться,
что в prompt осталось [REDACTED].
```

Почему хороший: есть файл и строка, есть правило, есть воспроизводимая проверка.

Уточнение по номеру строки: в примере из [`CASE.md`](CASE.md) указано `app/review_service.py:16`, но после применения `TRAINING_PR.diff` строка с подстановкой промпта — **14** (`self.llm.generate` — 15, `return {"comment": answer}` — 16). Пример в `CASE.md` задаёт форму комментария, а не разбор именно этого diff, поэтому номер оттуда нельзя переносить не пересчитав. В артефактах используются пересчитанные номера.

### Плохой пример

```text
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

Почему плохой: нет файла и строки, нет доказательства, нет проверки — нарушает `QA-1` и не укладывается в `OUT-1`.

### Что пока неизвестно

- Как именно `app.dependencies.review_service` создаётся: инстанс или фабрика под `Depends`. В diff видно только имя импорта.
- Целевая версия Python: аннотации `dict[str, str]` требуют ≥ 3.9, в diff версия не указана.
- Требуется ли аутентификация для `POST /api/reviews` — в diff нет, в правилах не оговорено.
- Какой провайдер LLM используется и какова его типичная задержка (нужно для проверки бюджета 10 с из `REL-1`).

## Как использовали AI

- Для чего: собрать AS IS по diff и отобрать в Context Pack только те правила [`CASE.md`](CASE.md), которые влияют на этот PR.
- Тип промпта: zero-shot для черновика (P1-01), затем master prompt для отбора правил (P1-02).
- Строка в [`prompts.md`](prompts.md): P1-01, P1-02.
- Что проверили и исправили сами: в zero-shot-ответе не было ни одного из семи правил — модель их не знала, поэтому пропустила нарушения `SEC-1` и `OUT-1`, самые серьёзные в этом PR. Сами построили таблицу «правило → состояние → доказательство» по каждой строке diff. Из Context Pack вручную убрали правила про `snake_case` и i18n как нерелевантные, а также отклонили предложенный моделью риск «дублирование префикса `/api`» — он не подтверждается diff и нарушает `QA-1`.
