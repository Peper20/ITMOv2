# E2E-проверки

Сквозной сценарий: ревьюер отправляет diff открытого PR и получает черновик, который может проверить, после чего сам принимает решение по PR (`SCOPE-1`). Проверяется вся цепочка — HTTP, редакция, вызов модели, сборка контракта, логирование — на развёрнутом сервисе. В качестве входа используется [`TRAINING_PR.diff`](TRAINING_PR.diff), чтобы результат был сопоставим с запусками P1-01 и P1-02 из [`prompts.md`](prompts.md).

| Сценарий пользователя | Предусловия | Действие | Наблюдаемый результат | Evidence |
|---|---|---|---|---|
| Позитивный: ревьюер получает проверяемый черновик | Сервис развёрнут, внешний LLM доступен, PR открыт | Отправить содержимое `TRAINING_PR.diff` в `POST /api/reviews` | HTTP 200 за ≤ 12 с. В теле `summary`, `risks` (1–3 элемента, у каждого `file`, `line`, `evidence`, `risk`) и непустой `checks`. Ревьюер открывает указанные `file:line` в diff и подтверждает каждое доказательство. Ожидаемо найдено нарушение `SEC-1` на `app/review_service.py:14` | Хороший пример из [`CASE.md`](CASE.md); правила `OUT-1`, `QA-1` |
| Позитивный: черновик приходит раньше ревьюера | PR только что открыт | Замерить время от отправки diff до получения ответа | Ответ ≤ 1 мин — целевое значение метрики «время до первой обратной связи» из [`problem.md`](problem.md) | Метрика в [`problem.md`](problem.md): было 4 ч ожидания ревьюера |
| Позитивный: решение остаётся за человеком | Черновик получен | Проверить состояние PR в GitHub после запроса | В PR нет approve, нет merge, нет автоматических комментариев и коммитов от сервиса. Ревьюер публикует замечания сам | Правило `SCOPE-1` |
| Негативный: секрет в diff | Diff содержит `api_token = "ghp_TESTSECRET0123456789"` | Отправить такой diff в `POST /api/reviews` | HTTP 200. В журнале обращений к внешнему провайдеру нет исходного токена — на его месте `[REDACTED]`. В ответе токен также не воспроизведён | Правило `SEC-1`; `app/review_service.py:14` |
| Негативный: внешний LLM недоступен | Провайдер отключён или отвечает ошибкой | Отправить валидный diff | Код ответа не 500. Тело валидно по `OUT-1`, `risks` пустой, `summary` сообщает, что разбор не выполнен. Ревьюер понимает, что нужно читать diff вручную, и не ждёт черновик | Правило `REL-1` |
| Негативный: некорректное тело запроса | Сервис доступен | Отправить `{"code": "..."}` без поля `diff` | HTTP 422 с описанием ошибки валидации; трассировка исключения наружу не попадает | `app/api.py` — `payload["diff"]` без валидации даёт 500 |
| Граничный: diff на пределе | Сервис доступен | Отправить `diff` длиной ровно 20 000 символов, затем 20 001 | 20 000 → HTTP 200 с валидным ответом; 20 001 → HTTP 413. Ревьюер получает понятное указание разделить PR | Правило `API-1` |
| Граничный: в diff нет проблем | Diff с косметическим изменением (например, правка комментария) | Отправить такой diff | HTTP 200, `risks` пустой, `summary` явно сообщает, что подтверждённых рисков нет. Ответ не содержит выдуманных замечаний вида «добавьте тесты» | Правило `QA-1`; плохой пример из [`CASE.md`](CASE.md) |
| Граничный: рисков больше трёх | Diff, нарушающий четыре и более правил | Отправить такой diff | В `risks` ровно три элемента, все с доказательствами; отброшенные риски не искажают `summary` | Правило `OUT-1`: максимум три элемента |
| Наблюдаемость после сквозного прогона | Выполнены все сценарии выше | Просмотреть логи сервиса | По каждому запросу есть `request_id`, длительность и статус. Ни содержимого diff, ни текста ответа модели в логах нет | Правило `OBS-1` |

## Критерий приёмки сквозного сценария

Сценарий считается пройденным, когда ревьюер смог по каждому возвращённому риску открыть указанные `file:line`, увидеть там процитированное `evidence` и выполнить предложенную проверку из `checks`. Если хотя бы один риск не удаётся подтвердить по diff или правилу репозитория, приёмка не пройдена: это нарушение `QA-1`, а не мелкое замечание к формулировке.

## Как использовали AI

- Строка в [`prompts.md`](prompts.md): P1-02.
- Что проверили и исправили сами: модель ограничилась позитивным сценарием и проверкой кода ответа. Сами добавили граничный случай «в diff нет проблем»: именно на нём проявляется склонность модели выдумывать замечания, и без него `QA-1` остаётся непроверенным. Сценарий «решение остаётся за человеком» добавили, потому что `SCOPE-1` нельзя подтвердить только телом ответа — нужно смотреть состояние PR в GitHub. Сценарий с секретом переписали: модель проверяла только тело ответа, тогда как утечка происходит в промпте, поэтому проверять нужно журнал обращений к провайдеру. Критерий приёмки сформулировали сами — без него «HTTP 200» ошибочно засчитывался бы как успех.
