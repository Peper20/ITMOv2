# Integration-проверки

Проверяем связки через `TestClient` FastAPI: HTTP-граница → DI → `ReviewService` → порт `LLM` (стаб, записывающий полученный промпт). Реальный внешний LLM не вызывается: нужен контролируемый вход, как и в [`CASE.md`](CASE.md).

| Связь компонентов | Что может сломаться | Как воспроизводим | Ожидаемый результат | Evidence |
|---|---|---|---|---|
| HTTP-граница → Pydantic-модель | Обращение к `payload["diff"]` даёт `KeyError` и 500 вместо 422 | `POST /api/reviews` с телом `{"code": "..."}` | HTTP 422, тело с описанием ошибки валидации, в ответе нет трассировки | `app/api.py` — `payload: dict` и `payload["diff"]` без валидации |
| HTTP-граница → проверка размера | Огромный diff проходит дальше и уходит в LLM | `POST` с `diff` длиной 20 001 символ | HTTP 413, внешний LLM не вызван (счётчик стаба = 0) | Правило `API-1` |
| HTTP-граница → проверка размера (граница) | Ложное срабатывание лимита | `POST` с `diff` ровно 20 000 символов | HTTP 200, стаб `LLM` вызван один раз | Правило `API-1` |
| `ReviewService` → внешний LLM | Секреты уходят за периметр | `POST` с diff, содержащим `ghp_TESTSECRET0123456789` и `-----BEGIN PRIVATE KEY-----` | В промпте, записанном стабом, нет ни одного секрета, есть `[REDACTED]`; HTTP 200 | `app/review_service.py:14`; хороший пример из [`CASE.md`](CASE.md) |
| `ReviewService` → сборка ответа | Клиент получает свободный текст вместо контракта | `POST` с валидным diff, стаб возвращает корректный черновик | HTTP 200; тело валидируется схемой `OUT-1`: `summary` (строка), `risks` (≤ 3, у каждого `file`, `line`, `evidence`, `risk`), `checks` (массив) | Сейчас возвращается `{"comment": answer}` |
| `ReviewService` → фильтр `QA-1` | В ответ попадает риск без доказательства | Стаб возвращает черновик, где два риска с evidence и два общих («добавьте тесты») | В `risks` только два подтверждённых риска | Плохой пример из [`CASE.md`](CASE.md) |
| `ReviewService` → внешний LLM (сбой) | Исключение всплывает как 500 | Стаб `LLM` бросает `ConnectionError` | Код ответа не 500; тело валидно по `OUT-1`; `risks` пустой; `summary` объясняет недоступность модели | Правило `REL-1`; `llm.generate` без `try/except` |
| `ReviewService` → внешний LLM (таймаут) | Запрос висит дольше бюджета | Стаб отвечает через 11 с | Ответ получен за ≤ 10 с + накладные; тело валидно по `OUT-1`, `risks` пустой | Правило `REL-1`: timeout 10 секунд |
| DI: `app.api` → `app.dependencies.review_service` | Импортируется фабрика вместо инстанса — `AttributeError` при первом запросе | Поднять приложение и выполнить один валидный `POST` | HTTP 200; подменённая через `dependency_overrides` зависимость получена обработчиком | `app/api.py` импортирует `review_service` как объект; устройство модуля в diff не видно |
| Приложение → лог | В лог попадает содержимое diff или ответ модели | `POST` с diff, содержащим `UNIQUE_MARKER_42`; перехват логов через `caplog` | В логах есть `request_id`, длительность, статус; нет `UNIQUE_MARKER_42` и текста ответа модели | Правило `OBS-1` |
| Регресс `/health` | Новый роут ломает существующий эндпоинт | `GET /health` после добавления `POST /api/reviews` | HTTP 200, тело `{"status": "ok"}` | `app/api.py` — `/health` в том же файле, что и новый роут |
| OpenAPI-схема | Контракт не описан, клиенты не могут сгенерировать модели | `GET /openapi.json` | Для `POST /api/reviews` описаны схема запроса с обязательным `diff` и схема ответа с `summary`, `risks`, `checks` | В diff нет `response_model` |

Инструмент: `pytest` + `fastapi.testclient.TestClient`; подмена зависимости через `app.dependency_overrides`.

## Как использовали AI

- Строка в [`prompts.md`](prompts.md): P1-02.
- Что проверили и исправили сами: модель предложила «протестировать эндпоинт с реальным LLM» — отклонили: без контролируемого стаба нельзя проверить ни `SEC-1` (не видно, что ушло в промпт), ни `REL-1` (не воспроизвести таймаут). Сами добавили проверку «внешний LLM не вызван при 413»: без неё тест на `API-1` проходит даже тогда, когда diff уже отправлен наружу, то есть после утечки. Регресс `/health` и проверку OpenAPI добавили вручную — модель ограничилась новым роутом. Проверку DI оставили в списке несмотря на неизвестное устройство `app.dependencies`: это зафиксировано как открытый вопрос в [`context.md`](context.md).
