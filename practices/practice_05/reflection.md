# Рефлексия

**Что согласовали**

Перед кодом закрыли шесть решений (R1–R6 в `project/specs/contracts/recurring.md`). Четыре из них
принял человек: набор периодов, форму ответа (`next` + `next_id`), «один шаг от срока» при
опоздании и «следующий остаётся» при снятии отметки. Два мелких решения принял оркестратор, с
пометкой в контракте. После согласования ни одна сторона в коде не разошлась с другой: UI ни
разу не вычислял дату сам, сквозной сценарий прошёл без правок кода.

**Чему научились**

- **Расхождения видны только при сверке двух черновиков.** Каждая спека по отдельности была
  аккуратной и прошла собственный чек-лист. Проблемы проявились, только когда положили рядом
  `ui-needs.md` и `api.md`. Пример — R2: по `next_id` UI не отличил бы «создан сейчас» от
  «создан раньше» и показывал бы «Следующий…» при каждой повторной отметке. Ни одна команда
  сама этого не заметила.
- **Самое важное — чего команда не спросила.** Вопрос об опоздании (R3) подняла только логика,
  UI о нём не думал. Без согласования это решение незаметно приняла бы реализация, причём
  вариант «пропускать периоды» требовал передавать `now` в слой БД.
- **Ревью находит ошибки и в самом контракте.** Команда логики заметила, что формулировка
  оркестратора «открытый экземпляр всегда один» противоречит R4. Та же фраза была в UI-спеке.
  Контракт — тоже артефакт, его надо проверять, а не только писать.
- **Спецификация по-настоящему проверяется сквозным тестом.** Сценарии из спек почти дословно
  стали проверками в браузере («двойной клик — один следующий», «обрыв связи — откат»). Поэтому
  проверка показывает, выполнены ли договорённости, а не только то, что код работает.
- **Фреймворк влияет на то, о чём думаешь.** OpenSpec подталкивает к вопросу «что меняется в
  уже описанном поведении» (delta, `MODIFIED`). Spec Kit — к вопросам «кто пользователь, что
  неясно, как измерить». Для маленькой кнопки второе избыточно, для договорённости двух
  команд — как раз нужно.

**Насколько SDD жизнеспособен**

Это вопрос с практики. SDD окупается там, где есть граница между сторонами: фронт и бэк, две
команды, публичный API. По сути это тот же API-first, только контракт пишется словами и
сценариями, а не одной OpenAPI-схемой. Для локальных правок цикл «спека → ревью → код → архив»
тяжёл: «Сбросить фильтры» заняла около 120 строк документов на 37 строк кода вместе с тестом. Дорогая часть
SDD — не генерация текста, а решения человека. Без них спека просто фиксирует догадки модели.

**Что бы сделал иначе**

- Отдельный агент-ревьюер для спек и для итоговой проверки, как на слайдах 9 и 11. Здесь
  ревью делал оркестратор, а проверяли автоматические тесты.
- Прогнать `speckit-analyze` (кросс-проверку spec/plan/tasks). Её роль выполнила ручная сверка.
- Для двух команд в OpenSpec попробовать один change с двумя capabilities (`ui` и `logic`) и
  сравнить, удобнее ли согласовывать в одном каталоге.
