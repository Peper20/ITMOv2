# Feature Specification: Повторяющиеся дедлайны — логика

**Feature Branch**: `001-recurring-logic`

**Created**: 2026-10-29

**Status**: Draft

**Input**: User description: "Повторяющиеся дедлайны. У дедлайна можно задать повтор (например, каждую неделю или каждый месяц). Когда повторяющийся дедлайн отмечают выполненным, появляется следующий." Зона этой спецификации — только логика (данные, правила, вычисление срока, API, валидация, сводка, экспорт). Интерфейс специфицирует другая команда.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Следующий экземпляр при выполнении (Priority: P1)

Пользователь заводит дедлайн «Отчёт по лабе» со сроком в понедельник 10:00 и повтором «каждую неделю». Отметив его выполненным, он сразу видит в списке новый открытый дедлайн «Отчёт по лабе» на следующий понедельник 10:00 — заводить его вручную не нужно.

**Why this priority**: это и есть фича; без неё повтор — просто метка.

**Independent Test**: создать дедлайн с повтором, перевести в «выполнено», проверить, что появился ровно один новый открытый дедлайн с правильным сроком и скопированными полями.

**Acceptance Scenarios**:

1. **Given** открытый дедлайн со сроком 2026-11-02T10:00 и повтором «еженедельно», **When** его отмечают выполненным, **Then** он становится выполненным, а появляется новый открытый дедлайн со сроком 2026-11-09T10:00, тем же названием, описанием, категорией, приоритетом и повтором.
2. **Given** дедлайн без повтора, **When** его отмечают выполненным, **Then** новых дедлайнов не появляется (поведение как сейчас).
3. **Given** выполненный дедлайн, у которого уже есть следующий, **When** отметку снимают и ставят снова, **Then** второй следующий не появляется.

---

### User Story 2 - Корректный срок в граничных датах (Priority: P1)

Пользователь, у которого дедлайн «каждый месяц 31-го» или «каждый год 29 февраля», получает следующий срок без «уползания» даты: короткие месяцы получают последний день месяца, а в длинных месяцах срок возвращается на исходное число.

**Why this priority**: ошибка в дате — молча неверный срок, худший дефект для трекера дедлайнов.

**Independent Test**: проверка функции вычисления следующего срока по таблице граничных случаев (см. Edge Cases) без участия интерфейса.

**Acceptance Scenarios**:

1. **Given** ежемесячный дедлайн 2027-01-31T23:59, **When** его выполняют, **Then** следующий — 2027-02-28T23:59; **When** выполняют и его, **Then** следующий — 2027-03-31T23:59.
2. **Given** ежегодный дедлайн 2028-02-29T09:00, **When** его выполняют, **Then** следующий — 2029-02-28T09:00, а после него — 2030-02-28T09:00 … 2032-02-29T09:00.
3. **Given** еженедельный дедлайн 2026-12-28T18:00, **When** его выполняют, **Then** следующий — 2027-01-04T18:00.

---

### User Story 3 - Управление повтором (Priority: P2)

Пользователь может включить, сменить или выключить повтор у существующего дедлайна, а при неверном значении получает понятную ошибку с указанием поля.

**Why this priority**: без редактирования повтор нельзя исправить или прекратить серию.

**Independent Test**: изменить повтор через редактирование, проверить сохранённое значение и ошибку на недопустимом значении.

**Acceptance Scenarios**:

1. **Given** дедлайн без повтора, **When** задают повтор «ежемесячно», **Then** повтор сохраняется, и при выполнении появляется следующий через месяц.
2. **Given** открытый дедлайн с повтором, **When** повтор выключают и отмечают дедлайн выполненным, **Then** следующий не появляется (серия завершена).
3. **Given** любой дедлайн, **When** передают недопустимое значение повтора, **Then** запрос отклоняется с ошибкой по полю повтора, данные не меняются.

---

### User Story 4 - Сводка и календарь согласованы с повтором (Priority: P3)

Сводка и экспорт в календарь показывают реальные экземпляры: выполненный — как выполненный, следующий — как обычный открытый дедлайн.

**Why this priority**: сопутствующее поведение; работает почти без изменений.

**Independent Test**: выполнить повторяющийся дедлайн и сравнить сводку и календарный файл до и после.

**Acceptance Scenarios**:

1. **Given** один открытый повторяющийся дедлайн, **When** его выполняют, **Then** в сводке «открыто» не меняется, «выполнено» растёт на 1.
2. **Given** выполненный повторяющийся дедлайн и его следующий экземпляр, **When** экспортируют календарь по умолчанию, **Then** в файле одно событие — следующий экземпляр, без правил повторения.

---

### Edge Cases

Вычисление следующего срока (время суток сохраняется всегда):

| Повтор | Текущий срок | Следующий |
|--------|--------------|-----------|
| ежедневно | 2026-12-31T08:00 | 2027-01-01T08:00 |
| ежедневно | 2028-02-28T08:00 | 2028-02-29T08:00 |
| еженедельно | 2026-12-28T18:00 | 2027-01-04T18:00 |
| ежемесячно | 2026-01-31 (опорный день 31) | 2026-02-28 |
| ежемесячно | 2028-01-31 (опорный 31) | 2028-02-29 |
| ежемесячно | 2026-02-28 (опорный 31) | 2026-03-31 |
| ежемесячно | 2026-04-30 (опорный 31) | 2026-05-31 |
| ежемесячно | 2026-12-15 | 2027-01-15 |
| ежегодно | 2028-02-29 (опорный 29) | 2029-02-28 |
| ежегодно | 2031-02-28 (опорный 29) | 2032-02-29 |

- **Опорный день**: число месяца из срока, заданного пользователем (при создании или смене срока/повтора). Следующий экземпляр наследует опорный день, а не «урезанное» число — иначе 31-е навсегда превратилось бы в 28-е.
- **Выполнили с опозданием** (следующий срок уже в прошлом): [NEEDS CLARIFICATION: создавать один следующий экземпляр строго по шагу от текущего срока (может сразу оказаться просроченным) или пропускать прошедшие периоды до первого срока позже текущего момента? Предлагаемое решение по умолчанию — пропускать до первого будущего.]
- **Снятие отметки** (выполнено → открыто): уже созданный следующий экземпляр остаётся. [NEEDS CLARIFICATION: удалять ли автоматически созданный следующий экземпляр, если пользователь его ещё не менял? По умолчанию — не удалять (нет потери данных).]
- **Повторная отметка** после снятия: новый экземпляр не создаётся, если следующий уже был создан и существует. Если следующий удалён — при повторной отметке он создаётся заново.
- **Переходы статуса**: следующий создаётся при любом переходе из «не выполнено» (todo, in_progress) в «выполнено». Изменение других полей у уже выполненного дедлайна следующий не создаёт.
- **Создание сразу выполненным** дедлайна с повтором: следующий не создаётся (правило срабатывает только на переход).
- **Удаление** открытого экземпляра завершает серию; удаление выполненного не затрагивает его следующий экземпляр.
- **Категория удалена**: следующий экземпляр копирует «без категории».
- **Срок за пределами допустимого календаря** (следующая дата после 9999-12-31): отметка «выполнено» отклоняется с ошибкой, данные не меняются.
- **Атомарность**: отметка «выполнено» и создание следующего — одна операция; либо обе, либо ни одна.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: У дедлайна MUST быть необязательный признак повтора с одним из значений: нет, ежедневно, еженедельно, ежемесячно, ежегодно. [NEEDS CLARIFICATION: нужны ли «ежедневно» и «ежегодно», или только «еженедельно» и «ежемесячно» из идеи заказчика? По умолчанию — все четыре: ежегодно нужно для случая 29 февраля, ежедневно ничего не стоит.] Интервал всегда 1 (каждые 2 недели и т. п. — вне объёма).
- **FR-002**: Существующие дедлайны после обновления MUST остаться без повтора и вести себя как раньше.
- **FR-003**: При переходе дедлайна с повтором в «выполнено» система MUST создать ровно один следующий экземпляр, если у этого дедлайна ещё нет существующего следующего.
- **FR-004**: Следующий экземпляр MUST копировать название, описание, категорию, приоритет, повтор и опорный день; статус — «к выполнению»; отметка о выполнении — пустая; даты создания/изменения — текущий момент.
- **FR-005**: Срок следующего экземпляра MUST вычисляться по правилам: ежедневно +1 день, еженедельно +7 дней, ежемесячно — следующий месяц, ежегодно — тот же месяц следующего года; число = опорный день, а если его нет в месяце — последний день месяца; время суток неизменно.
- **FR-006**: Выполненный дедлайн MUST хранить ссылку на свой следующий экземпляр, и она MUST быть видна в ответе; при удалении следующего ссылка очищается.
- **FR-007**: Снятие отметки «выполнено» MUST NOT удалять и изменять следующий экземпляр (см. уточнение в Edge Cases).
- **FR-008**: Пользователь MUST иметь возможность задать, сменить и выключить повтор при создании и редактировании; смена срока или повтора переустанавливает опорный день по новому сроку.
- **FR-009**: Недопустимое значение повтора MUST отклоняться ошибкой валидации с указанием поля повтора и перечнем допустимых значений; ссылку на следующий экземпляр нельзя задать вручную.
- **FR-010**: Сводка MUST считать экземпляры как обычные дедлайны, без новых показателей.
- **FR-011**: Экспорт в календарь MUST выгружать экземпляры как отдельные события без правил повторения (каждый экземпляр — своё событие со своим идентификатором).
- **FR-012**: Изменения после выполнения MUST быть атомарными: при ошибке создания следующего экземпляра отметка «выполнено» не сохраняется.

### Key Entities

- **Дедлайн** (существующая сущность) + новые атрибуты:
  - *повтор* — нет / ежедневно / еженедельно / ежемесячно / ежегодно;
  - *опорный день* — число месяца 1–31, служебный, наружу не выдаётся;
  - *следующий экземпляр* — ссылка на дедлайн, созданный при выполнении этого (только чтение).
- **Серия** — цепочка дедлайнов, связанных ссылками «следующий»; отдельной сущностью не хранится.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Для 100% случаев из таблицы Edge Cases вычисленный срок совпадает с ожидаемым.
- **SC-002**: После выполнения повторяющегося дедлайна следующий доступен сразу, без отдельного действия пользователя (0 дополнительных шагов).
- **SC-003**: Любая последовательность «отметить / снять отметку», повторённая до 10 раз, оставляет ровно один следующий экземпляр.
- **SC-004**: После обновления 100% ранее созданных дедлайнов открываются и редактируются без ошибок и не имеют повтора.
- **SC-005**: Сводка и календарь после выполнения повторяющегося дедлайна отражают ровно один открытый экземпляр серии.

## Assumptions

- Однопользовательское локальное приложение; время локальное без часовых поясов, поэтому перехода на летнее время нет и «+1 день» — ровно календарные сутки.
- Повтор привязан к сроку экземпляра, а не к моменту выполнения.
- Будущие экземпляры заранее не создаются: в каждый момент у серии не больше одного «автоматического» открытого экземпляра (пользователь может сделать больше, снимая отметки).
- Конец серии (дата окончания, число повторов) — вне объёма.
- Фильтр списка «только повторяющиеся» — вне объёма; при необходимости его запросит UI-команда.
- Время ответа и объём данных не меняются заметно: создаётся не более одной записи на отметку.
- Расхождения с UI-спецификацией (набор периодов, названия полей) решает человек при согласовании контракта (`contracts/api.md`).
