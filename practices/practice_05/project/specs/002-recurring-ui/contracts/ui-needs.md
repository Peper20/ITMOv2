# Что UI ждёт от бэкенда: повторяющиеся дедлайны (черновик команды UI)

> **Заменён** общим контрактом [../../contracts/recurring.md](../../contracts/recurring.md) (2026-10-29, решения R1–R6). Ниже — исходный черновик UI, оставлен для истории.

Черновик стороны UI для общего контракта. Основа — текущий API (README, `frontend/src/lib/api.ts`):
JSON под `/api`, ошибки `{"error": "<текст для человека>", "field": "<поле>"}`. Названия полей —
предложение; окончательные фиксируются в общем `contracts/` после согласования (constitution, II).

## 1. Данные

### Deadline — новое поле

| Поле | Тип | Значения | Зачем UI |
|---|---|---|---|
| `recurrence` | `string \| null` | `null` — не повторяется; `"daily"`, `"weekly"`, `"monthly"` | значение поля «Повтор», значок и озвучка |

- Поле есть во **всех** ответах с дедлайнами: `GET /api/deadlines`, `GET/POST/PATCH /api/deadlines/{id}`.
- У существующих после миграции дедлайнов — `null`.
- Тексты вариантов («Каждую неделю» и т. п.) UI держит сам; бэкенд отдаёт только код.
- Неизвестный код от сервера (на будущее): UI показывает значок и «повторяется», в списке — «Другой повтор» (только для чтения).

```ts
export type Recurrence = "daily" | "weekly" | "monthly";
export interface Deadline { /* …существующие поля… */ recurrence: Recurrence | null; }
export interface DeadlineInput { /* … */ recurrence?: Recurrence | null; }
```

### Ответ на отметку «выполнено» — следующий экземпляр

UI должен **в том же ответе** узнать, создан ли следующий и на какой срок (FR-005, FR-010), без
отдельного запроса и без своего вычисления даты.

Предложение: `PATCH /api/deadlines/{id}` возвращает обычный `Deadline` плюс поле `next`:

```json
{ "id": 12, "status": "done", "recurrence": "weekly", "...": "...",
  "next": { "id": 31, "title": "Отчёт", "due_at": "2026-11-13T18:00", "status": "todo",
            "recurrence": "weekly", "category_id": 2, "priority": 2, "...": "..." } }
```

- `next` — полный `Deadline` созданного экземпляра, если этот PATCH перевёл повторяющийся дедлайн
  в `done`; иначе `null` (или поля нет). UI берёт из него `id` и `due_at`.
- Код ответа как сейчас — `200`.
- `POST /api/deadlines` с `status: "done"` и повтором: если бэкенд тоже создаёт следующий — тот же `next` в ответе.

## 2. Вызовы, которые делает UI

| Действие UI | Вызов | Тело |
|---|---|---|
| Создать с повтором (окно) | `POST /api/deadlines` | `{..., "recurrence": "weekly"}` |
| Быстрое добавление | `POST /api/deadlines` | без `recurrence` → сервер ставит `null` |
| Изменить/снять повтор | `PATCH /api/deadlines/{id}` | `{"recurrence": "monthly"}` / `{"recurrence": null}` |
| Отметить выполненным (флажок, кнопка) | `PATCH /api/deadlines/{id}` | `{"status": "done"}` |
| Сохранить окно со статусом «Выполнен» | `PATCH /api/deadlines/{id}` | все поля формы, включая `status: "done"` |
| Вернуть в работу | `PATCH /api/deadlines/{id}` | `{"status": "todo"}` |
| Удалить | `DELETE /api/deadlines/{id}` | — (удаляет только этот экземпляр) |
| Обновить экран после любого из действий | `GET /api/deadlines?from&to&sort=due` (+фильтры), `GET /api/stats`, `GET /api/deadlines?status=open&to=…` | как сейчас |

Фильтры списка новых параметров не требуют.

## 3. Ошибки и как UI их показывает

| Ситуация | Ответ, который ждёт UI | Что показывает UI |
|---|---|---|
| Неизвестное значение повтора | `400 {"error": "Повтор: выберите один из вариантов.", "field": "recurrence"}` | текст под полем «Повтор», фокус на поле, окно открыто |
| Повтор у дедлайна без валидного срока | `400` с `field: "due_at"` | под полем даты (как сейчас) |
| Дедлайн не найден (удалён в другой вкладке) | `404` | молча закрыть окно и обновить (как сейчас) |
| Повторная отметка `done` уже выполненного (двойной клик, повтор после обрыва) | `200`, статус `done`, `next: null`, **второй экземпляр не создаётся** (идемпотентно) | без сообщения о следующем, просто обновить |
| Не удалось создать следующий | `5xx`, **и** текущий не должен остаться `done` (всё или ничего) | полоса ошибки «Сервер не смог выполнить запрос…» с «Повторить», флажок откатывается |
| Нет связи | — (fetch упал, `ApiError(0)`) | полоса ошибки с «Повторить», флажок откатывается; после «Повторить» состояние берётся с сервера |

Тексты в `error` — на русском, для человека (их UI показывает как есть).

## 4. Состояния UI и что нужно от бэкенда

| Состояние | Что нужно |
|---|---|
| Загрузка периода | ничего нового: `recurrence` приходит в списке |
| Отметка в процессе | один запрос на одно нажатие; UI блокирует повторные |
| Успех с повтором | `next.due_at` в ответе → сообщение «Следующий — пт, 13 нояб., 18:00», «Показать» → переход к дню `next.due_at` |
| Успех без повтора | `next: null` → как сейчас |
| Пусто / отфильтровано | ничего нового; следующий наследует `category_id` и `title` от исходного |

## 5. Вопросы к команде логики

1. Набор правил: только `daily/weekly/monthly` или ещё `yearly`, интервал («каждые 2 недели»)?
2. Срок следующего считается от исходного `due_at` или от момента выполнения? Что с 31-м числом и 29 февраля? (UI покажет любую дату из `next`, но хочет знать для подсказок.)
3. Снятие `done` (`{"status": "todo"}`) у дедлайна, который уже породил следующий: следующий удаляется, остаётся или запрос отклоняется (`409`)? Если удаляется — UI нужно знать это из ответа (например, `removed_next_id`), чтобы сказать пользователю.
4. Что наследует следующий: название, заметки, категория, приоритет, повтор — да; время суток — то же?
5. Нужна ли связь экземпляров серии в данных (например, `series_id`) — UI в первой версии она не нужна.
