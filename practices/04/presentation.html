MCP — Model Context Protocol

MCP — открытый стандарт для подключения AI-приложений к внешним системам. Через него LLM вызывает инструменты (tools) внешних программ для получения информации или выполнения действий.

Проблема N×N: без стандарта каждая интеграция (Claude + GitHub, ChatGPT + Slack, Cursor + PostgreSQL) требует уникального кода. 5 AI-клиентов × 5 сервисов = 25 интеграций. С MCP: 5 + 5 = 10 — каждый MCP-сервер пишется один раз и работает с любым клиентом, поддерживающим протокол. Один MCP-сервер PostgreSQL = работает в Roo Code, Cursor, Claude Code, OpenCode — без изменений. Сервер не знает, какой клиент к нему подключён.

Метафора: «USB-C для искусственного интеллекта» —
один разъём, любое устройство.

Model Context Protocol

Создан Anthropic (ноябрь 2024)
Передан в Agentic AI Foundation при Linux Foundation (декабрь 2025)
Поддерживают: Roo Code, Claude Code, Cursor, OpenCode и др.

Ключевое преимущество MCP — детерминизм. LLM решает какой tool вызвать (недетерминированно), но сам tool — обычный код: тот же вызов → тот же результат. MCP отделяет принятие решений от исполнения.

Транспортный уровень

STDIO — локальные серверы

Host запускает сервер как дочерний процесс, общение через stdin/stdout. Именно это мы делаем в .roo/mcp.json с "command": "npx".

Быстро, без сети. Подходит для 99% задач в IDE.

Streamable HTTP — удалённые серверы

HTTP/HTTPS + Server-Sent Events для стриминга. MCP-сервер хостится удалённо (облако, другой сервер) — агент обращается к нему по URL. Сервер может работать с production-БД, но это решение администратора: вы сами определяете, к какой БД подключён MCP-сервер.

Для SaaS-интеграций: Slack, Jira, продакшен-БД. В учебных целях — всегда dev/staging.

Human-in-the-loop: спецификация обязывает UI запрашивать подтверждение перед вызовом tool. В Roo Code — Approve/Reject (или auto-approve). В Claude Code — аналогично (--dangerously-skip-permissions отключает).
MCP Inspector — бесплатный инструмент для отладки серверов в браузере: modelcontextprotocol.io

Каждый MCP-сервер может предоставлять три типа примитивов:

Tools (инструменты)

Функции, которые модель вызывает для совершения действий. Основной примитив.

model-controlled

Resources (ресурсы)

Источники данных, которые модель может читать. Аналог GET-эндпоинтов.

Файлы проекта
Таблицы базы данных
Содержимое документов

application-controlled

Prompts (промпты)

Готовые шаблоны запросов, оптимизированные для работы с данным сервером.

user-controlled

MCP-серверы, которые я использую на практике

Context7 context7.com

Проблема: LLM обучены на старых данных. Go 1.25+ добавил wg.Go(func() {...}), но без Context7 LLM генерит устаревший wg.Add(1); go func() { defer wg.Done()... }. Аналогично: Pydantic v2 vs v1, SQLAlchemy 2.0 async vs sync.

Почему не curl / исходники: агент может скачать доки или прочитать исходный код установленной библиотеки. Но: сырой HTML — тысячи токенов мусора; исходники — implementation detail, а не документация. Пример: миграция SQLAlchemy 1.x → 2.0 async не вычитывается из site-packages/ за разумное число токенов.

Как работает: вы указываете библиотеку → Context7 резолвит её в своей базе → отдаёт компактную документацию нужной версии → детерминированно, одни и те же доки каждый раз.

API: resolve (найти библиотеку) → get-library-docs (получить документацию)

PostgreSQL MCP GitHub

Зачем: агент может подключиться к БД через терминал, но каждый раз пишет скрипт заново (недетерминированно). MCP даёт фиксированный API: query(sql) → всегда один и тот же код → предсказуемый JSON.

API: query (выполнить read-only SQL → JSON). Это единственный tool в @modelcontextprotocol/server-postgres. Агент сам пишет нужные SQL-запросы: SELECT table_name FROM information_schema.tables для списка таблиц, \d+ table для схемы

Юзкейс: при дебаге агент сам проверяет данные в БД, видит схему таблиц, находит расхождения между моделью и реальной таблицей.

Sequential Thinking GitHub

Главная ценность — компенсация слабых моделей. Claude Code и Cursor нативно декомпозируют задачи (extended thinking). Но если вы используете модель через прокси (vsellm.ru) или Open Source модель без нативного CoT — Seq. Thinking даёт похожий эффект внешним инструментом. Заставляет модель думать пошагово → более качественный результат.

Экстернализация плана: план записывается в tool calls → вы видите каждый шаг и можете вмешаться. В отличие от «думания в голове», план доступен для ревью.

API: sequentialthinking (создать/обновить шаг плана с возможностью ревизии)

A/B: «Добавь Rate Limiter» → без ST агент забывает Redis-ключи, fail-open, заголовки. С ST — план из 7 шагов, ничего не пропускает.

Честный take: если работаете с топовыми моделями в Claude Code — ST не нужен. Если через прокси или с OSS-моделями — ST компенсирует отсутствие нативного планирования и помогает слабым моделям выдавать более качественный результат.

Как агент узнаёт о MCP tools? При старте каждый MCP-сервер декларирует свои tools: имя, описание, JSON Schema параметров. Эти описания инжектируются в системный промпт агента. Skills — что это?

Skills — папки с инструкциями, скриптами и ресурсами. Ключевая фича: агент автоматически выбирает нужный скил, сопоставляя ваш промпт с description в YAML frontmatter (YAML frontmatter — метаданные в начале Markdown-файла между тройными дефисами ---. Аналог <head> в HTML для Markdown).

В отличие от tools (выполняют действие → возвращают результат), skills подготавливают агента к решению задачи — инжектируют инструкции в контекст.

Структура папки скила

├── resources/    # Шаблоны, примеры, данные
│   ├── schema_template.py
│   └── example_router.py
└── scripts/      # Исполняемый код (Python, Bash)
    └── generate_crud.py

Progressive Disclosure — экономия контекста

Ключевой механизм: агент не загружает все скилы сразу. Сначала он видит только метаданные (~100 токенов на скил). Полные инструкции подгружаются только когда скил релевантен задаче.

Шаг 1: Агент видит name + description
~100 токенов × N скилов
↓ совпадение с задачей
Шаг 2: Загрузка полного SKILL.md
до нескольких тысяч токенов инструкций
↓ по мере необходимости
Шаг 3: Загрузка resources/ и scripts/
практически без ограничений по объёму
Сравните с MCP: MCP загружает описания всех tools сразу в системный промпт. Один MCP tool с описанием и JSON Schema — ~200–500 токенов. 3 сервера (Context7 + PostgreSQL + Seq. Thinking, ~6 tools) ≈ 1500–2500 токенов. 10 серверов — легко 10–20k токенов в каждом запросе, даже если вы их не используете. Skills экономнее за счёт progressive disclosure.

Технические лимиты

Метаданные (frontmatter)

name — до 64 символов

description — до 1 024 символов

Попадают в контекст первыми — пишите максимально точно

Тело SKILL.md

Рекомендуемый объём — до нескольких тысяч токенов инструкций (точный лимит зависит от версии Roo Code)

Достаточно для развёрнутого чеклиста из 15–20 шагов

Ресурсы и скрипты

resources/ и scripts/ — практически без лимита

Подгружаются по мере необходимости, не раздувают контекст

Контекст — ограниченный ресурс. 10 MCP-серверов × 2000 токенов описаний = 20k токенов «на старте». Skills с progressive disclosure — значительно дешевле.
Можно ли отключить загрузку MCP? В Roo Code — нельзя выборочно: если сервер подключён, его tools попадают в контекст. Решение: отключите ненужные серверы (toggle в UI) или удалите из mcp.json. В Claude Code — аналогично. Идеальный вариант: скил указывает нужные MCP, а сами MCP подключаются только при активации скила — но пока это не реализовано.

Debug Mode — дебаг как специализированный агент

Обычный подход к дебагу через LLM: «вот ошибка, почини». Агент угадывает причину и генерит сотни строк спекулятивного кода. Debug Mode — это отдельный агентный цикл, построенный на рантайм-данных, а не на догадках.

Цикл Debug Mode (Cursor)

1

Гипотезы

Агент читает код, генерит 3–5 тестируемых гипотез о причине бага

2

Инструментация

Вставляет таргетированные логи для проверки каждой гипотезы. Не «добавь console.log», а логи с тегами [H1], [H2]

3

Воспроизведение + анализ

Вы воспроизводите баг → агент анализирует рантайм-логи → точечный фикс (2–3 строки, не сотни)

4

Верификация + cleanup

Вы подтверждаете фикс → агент удаляет всю инструментацию → чистый diff

Почему это работает лучше

Без Debug Mode

«Вот ошибка → вот фикс» — pattern matching по тексту ошибки. Race conditions, state bugs, timing issues — невидимы без рантайма.

С Debug Mode

Агент видит реальные значения переменных, порядок выполнения, тайминги. Фикс основан на данных, а не на догадках.

Memory Bank — память проекта между сессиями

Проблема «чистого листа»: LLM — гениальный стажёр

LLM обладает колоссальным объёмом общих знаний, но страдает от отсутствия оперативной памяти. Каждый новый чат = чистый лист. Агент забывает архитектурные решения, паттерны, прогресс. У него нет доступа к вашему коду, вики и соглашениям — он «заморожен во времени» на дату обучения.

Наивно: копипаста

Копировать контекст в каждый чат, CLAUDE.md, memory.md. Не масштабируется, быстро устаревает, забываешь обновлять.

Memory Bank (Markdown)

Что: 6 Markdown-файлов в memory-bank/. Агент читает в начале сессии, обновляет в конце.

Как: правила в .roo/rules.md — «В начале сессии прочитай memory-bank/. В конце — обнови activeContext и progress».

Когда: малые/средние проекты (до ~100 файлов). Ноль инфраструктуры.

projectbrief.md productContext.md activeContext.md systemPatterns.md techContext.md progress.md

RAG (Qdrant, ChromaDB)

Что: Retrieval-Augmented Generation. Код/доки индексируются через embedding-модели → семантический поиск по смыслу, а не по ключевым словам.

Как: embedding-модель (OpenAI, Voyage) → векторная БД (Qdrant) → MCP-сервер для доступа агента. Запрос «как мы обрабатываем ошибки?» → релевантные фрагменты кода.

Когда: 10k+ файлов, monorepo, legacy. Требует инфраструктуры (Docker, embedding API).

⚠ Риски: «лотерея поиска» — похожие, но бесполезные фрагменты вытесняют нужные. Данные есть в базе, но модель их не видит (silent failure). Reranker частично решает.

MCP Memory Server

Что: MCP-сервер для хранения/извлечения знаний. Агент вызывает store_memory / retrieve_memory как обычные MCP tools.

Как: @modelcontextprotocol/server-memory — хранит key-value пары. Или кастомный сервер с persistent storage.

Когда: межпроектная память, команда, нужен API-доступ к знаниям.

Для нашего курса: начинаем с memory.md — один файл, ноль инфраструктуры, максимум пользы. Создайте скил, который будет обогащать memory.md только когда вы попросите — «обнови memory». Это ваша ручная память, за которой вы следите сами.
MCP Memory — разные варианты: @modelcontextprotocol/server-memory (key-value, entities + relations), mem0 (semantic memory с embedding), claude-memory (persistent memory для Claude Code). Поддерживают разные типы ключей (entities, relations, observations). Выберите то, что подходит вашему проекту.
Cursor Codebase Indexing: в Cursor есть индексация кодовой базы из коробки — весь проект индексируется через embeddings и доступен агенту через @codebase. Данные хранятся на серверах Cursor (облако). Roo Code такого нативного решения не имеет — компенсируем через Memory Bank и RAG.

/compact — сжатие контекста на лету

Memory Bank решает проблему между сессиями. Но что делать, когда контекст переполняется внутри сессии? После 70–80k токенов качество падает: проблема «lost in the middle» в современных моделях в целом решена — агент не забывает ранние инструкции буквально. Однако он становится более склонен к галлюцинациям: чем больше контекст, тем выше вероятность ошибочных выводов и неточных ответов.

Что делает compact

Берёт всю историю диалога → суммаризирует ключевые решения, файлы, прогресс → начинает новую сессию с этой суммаризации вместо полной истории. Контекст сжимается в 3–5×, но ключевые решения сохраняются.

Compact ≠ Clear

/clear = чистый лист, полная потеря контекста.
/compact = «умное забывание» — агент помнит что решили, забывает как обсуждали.

Когда компактить: на 70–75% контекста (не на 90%!), на логических точках (фича готова, переход к следующей), перед сменой контекста задачи.

Cursor Авто-сжатие при 100%. /compress для ручного. Бонус: сохраняет полный лог как файл, агент ищет через grep
Roo Code Intelligent Context Condensing (v3.19+). Кнопка «Condense Context» в UI + авто-порог (слайдер в настройках). Кастомизируемый промпт сжатия

ITMO | 2026 Блок 7 — Хуки

Проблема: LLM не следует инструкциям на 100%

На Практике 01 мы ввели детерминированный feedback loop: код → линтер → тесты → авто-фикс. Но кто гарантирует, что агент запустит линтер?

Инструкции в rules = ~70–80%

Правило «всегда запускай ruff check перед коммитом» в .roo/rules/ — это совет модели. LLM может проигнорировать: забыть, переключиться на другую задачу, обрезать при переполнении контекста.

Хуки = 100%

Хук — shell-команда, срабатывающая автоматически при событии (файл записан, агент завершает работу). AI не запрашивает хук — хук перехватывает AI.

Аналогия: rules — это «пожалуйста, мой руки перед едой». Хуки — кран с автоматическим датчиком, который включается сам.

Масштаб проблемы

47–76%

задач кодогенерации не дают семантически эквивалентного результата при повторном запуске одного промпта (Ouyang et al., ACM TOSEM 2025; разброс зависит от бенчмарка и temperature)

5–15%

разброс точности между запусками даже при temperature=0 (до 15% — worst-case с Chain-of-Thought; типично 5–10%)

Причины: планирование GPU-ядер, точность float, размер батча. Даже при temperature=0 детерминизм не гарантирован — это особенность инференса, а не настройки.

ITMO | 2026 Блок 7 — Хуки

Нет хуков? → pre-commit + частые коммиты

Roo Code и некоторые другие IDE не поддерживают хуки. Но принцип «детерминированная проверка вокруг недетерминированной генерации» можно реализовать через git hooks — в частности, pre-commit. 

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.9.9
    hooks:
      - id: ruff            # линтер
      - id: ruff-format     # форматтер
  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.14.0
    hooks:
      - id: mypy            # type checker
  - repo: local
    hooks:
      - id: pytest
        name: run tests
        entry: pytest --tb=short -q
        language: system
        pass_filenames: false

Как это работает с AI-агентом

1

В rules: «коммить после каждого логического изменения»

Агент делает git commit часто → pre-commit хук срабатывает каждый раз

2

pre-commit запускает линтер + тесты

Если проверки не прошли → git commit блокируется → агент видит ошибку в терминале

3

Агент исправляет и пробует снова

Diagnostics Integration в Roo Code подхватит ошибки VS Code → feedback loop замыкается

Ограничения: pre-commit срабатывает только при git commit, а не после каждого редактирования. Если агент пишет 10 файлов и коммитит в конце — ошибки обнаружатся поздно. Настоящие хуки (Claude Code) ловят ошибку сразу после записи файла.
Вывод: pre-commit — «80% решение». Не идеально, но лучше, чем ничего. Установка: pip install pre-commit && pre-commit install. Работает с любой AI IDE, включая Roo Code.
